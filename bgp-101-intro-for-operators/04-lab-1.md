# Lab 1 - Establishing Basic BGP Connectivity

## Objectives
- Configure a basic eBGP session between two routers.
- Verify the BGP Finite State Machine (FSM) transitions.
- Originate and verify a prefix announcement.
- Inspect BGP Path Attributes (AS_PATH, NEXT_HOP).

## Working with the Lab Environment

All labs run [FRR](https://frrouting.org/) routers as containers orchestrated by [Containerlab](https://containerlab.dev/), so you need a Linux machine (or VM) with Docker and Containerlab installed. Each lab lives in its own directory under `labs/`:

| Path | Contents |
| :--- | :--- |
| `labs/lab-N/lab-N.clab.yml` | The Containerlab topology. |
| `labs/lab-N/configs/` | The starting configuration of each router: hostname and interface addresses, and for routers you don't operate (ISPs, customers), their full configuration. |
| `labs/lab-N/solution/` | The finished configuration of each router. |
| `labs/daemons`, `labs/vtysh.conf` | FRR settings shared by all labs (they enable `bgpd`, `ospfd` and `ospf6d`). |

Useful commands:

```bash
cd labs/lab-1
sudo containerlab deploy                                  # start the lab
docker exec -it clab-bgp101-lab1-router-a vtysh           # router CLI
docker exec clab-bgp101-lab1-router-a ping -c 3 10.0.0.2  # shell commands
sudo containerlab destroy                                 # tear it down
../load-solution.sh lab-1                                 # apply the solution
```

A few things to keep in mind:

- Use `ping` and `traceroute` from the container shell as shown above. The `ping` command inside `vtysh` doesn't stop on its own.
- The starting configurations are mounted read-only, so `write memory` fails on purpose and your changes are lost when the lab is destroyed. To keep your work, save the running configuration from the host: `docker exec clab-bgp101-lab1-router-a vtysh -c 'show running-config' > router-a.txt`.
- `load-solution.sh` applies the finished configuration on top of the running one. It is meant for instructors, or for comparing your work at the end of a lab.

## Topology
We will use a simple point-to-point topology:

- **Router A (AS 65001)**
  - Interface eth1: 10.0.0.1/30
  - Loopback: 10.255.0.1/32
- **Router B (AS 65002)**
  - Interface eth1: 10.0.0.2/30
  - Loopback: 10.255.0.2/32

The interfaces are already addressed when the lab starts.

## Step 1: Connectivity Check
Before BGP can establish a session, the underlying IP connectivity must be functional.

```text
$ docker exec clab-bgp101-lab1-router-a ping -c 3 10.0.0.2
PING 10.0.0.2 (10.0.0.2): 56 data bytes
64 bytes from 10.0.0.2: seq=0 ttl=64 time=0.098 ms
64 bytes from 10.0.0.2: seq=1 ttl=64 time=0.121 ms
64 bytes from 10.0.0.2: seq=2 ttl=64 time=0.091 ms
```

## Step 2: BGP Configuration
Configure the BGP process and the neighbor relationship. Enter `vtysh` on each router and type `configure terminal` first.

### Router A
```text
router bgp 65001
 bgp router-id 10.255.0.1
 neighbor 10.0.0.2 remote-as 65002
 address-family ipv4 unicast
  network 10.255.0.1/32
 exit-address-family
```

### Router B
```text
router bgp 65002
 bgp router-id 10.255.0.2
 neighbor 10.0.0.1 remote-as 65001
 address-family ipv4 unicast
  network 10.255.0.2/32
 exit-address-family
```

## Step 3: Verifying the Session
Observe the BGP state. It should move through `Connect`/`Active` and `OpenSent` to `Established`. Once established, the `State/PfxRcd` column shows the number of prefixes received instead of a state name.

```text
router-a# show ip bgp summary
...
Neighbor        V         AS   MsgRcvd   MsgSent   TblVer  InQ OutQ  Up/Down State/PfxRcd   PfxSnt Desc
10.0.0.2        4      65002         3         3        1    0    0 00:00:07     (Policy) (Policy) N/A
```

The session is up, but no routes are exchanged. **`(Policy)` is FRR's safe default at work**: following [RFC 8212](https://datatracker.ietf.org/doc/html/rfc8212), FRR neither accepts nor sends any route over an eBGP session that has no inbound and outbound policy. We will write real policies in Lab 3. For now, turn the check off on both routers:

```text
router bgp 65001
 no bgp ebgp-requires-policy
```

The change only affects new updates, so ask for a refresh with a soft reset (Chapter "Announcing My Routes" explains what this does):

```text
router-a# clear ip bgp * soft
router-a# show ip bgp summary
...
Neighbor        V         AS   MsgRcvd   MsgSent   TblVer  InQ OutQ  Up/Down State/PfxRcd   PfxSnt Desc
10.0.0.2        4      65002         7         8        2    0    0 00:00:34            1        2 N/A
```

## Step 4: Inspecting Attributes
Check how the prefixes appear in the BGP table and note the attributes discussed in the "Path Attributes and Best Path Selection" chapter.

```text
router-a# show ip bgp
BGP table version is 2, local router ID is 10.255.0.1, vrf id 0
Default local pref 100, local AS 65001
Status codes:  s suppressed, d damped, h history, u unsorted, * valid, > best, = multipath,
               i internal, r RIB-failure, S Stale, R Removed
Nexthop codes: @NNN nexthop's vrf id, < announce-nh-self
Origin codes:  i - IGP, e - EGP, ? - incomplete
RPKI validation codes: V valid, I invalid, N Not found

     Network          Next Hop            Metric LocPrf Weight Path
 *>  10.255.0.1/32    0.0.0.0                  0         32768 i
 *>  10.255.0.2/32    10.0.0.2                 0             0 65002 i
```

**Observations:**

- **AS_PATH:** Notice the `Path` attribute for `10.255.0.2/32` shows `65002`.
- **NEXT_HOP:** The `Next Hop` for the remote prefix is the interface IP of Router B. `0.0.0.0` marks the route Router A originated itself.
- **ORIGIN:** The `i` at the end indicates the route was originated inside the AS (the `network` command).
- **Weight:** Locally originated routes get a weight of 32768, so they always win on this router.

Look at a single prefix in detail, and confirm that the route made it into the routing table:

```text
router-a# show ip bgp 10.255.0.2/32
BGP routing table entry for 10.255.0.2/32, version 2
Paths: (1 available, best #1, table default)
  Advertised to peers:
  10.0.0.2
  65002
    10.0.0.2 from 10.0.0.2 (10.255.0.2)
      Origin IGP, metric 0, valid, external, best (First path received)

router-a# show ip route bgp
...
B>* 10.255.0.2/32 [20/0] via 10.0.0.2, eth1, weight 1, 00:00:04
```

Finally, test the data plane between the loopbacks:

```text
$ docker exec clab-bgp101-lab1-router-a ping -c 3 -I 10.255.0.1 10.255.0.2
```

**Question:** `PfxSnt` in the summary says Router A sends *two* prefixes to Router B, and `show ip bgp neighbors 10.0.0.2 advertised-routes` confirms that it advertises `10.255.0.2/32` back to the router it learned it from. Why doesn't this create a loop? (Hint: look at the AS_PATH Router B receives.)

## Step 5: Breaking the Session
Sessions only come up when both ends agree on the parameters. On Router B, replace the neighbor with one that expects the wrong AS:

```text
router bgp 65002
 no neighbor 10.0.0.1
 neighbor 10.0.0.1 remote-as 65009
```

Watch the session on Router A. Router B rejects Router A's OPEN with a NOTIFICATION and the session falls back to `Idle`:

```text
router-a# show ip bgp neighbors 10.0.0.2
...
  BGP state = Idle
...
  Last reset 00:00:13,  Notification received (OPEN Message Error/Bad Peer AS)
```

Fix the neighbor on Router B (remote AS 65001) and watch the session come back up. Since you deleted the neighbor, you don't need to soft-reset this time.
