# Lab 2 - iBGP, MP-BGP, and Route Origination

## Objectives
- Establish an iBGP session using Loopback interfaces.
- Originate IPv4 and IPv6 prefixes using the `network` command and "Anchoring".
- Observe and fix the iBGP Next-Hop issue using `next-hop-self`.
- Perform controlled redistribution from an IGP into BGP.
- Use soft-reset techniques to apply policy changes.

## Topology & Addressing
We will use a 3-router topology in Containerlab:

| Device | Interface    | IPv4 Address | IPv6 Address      | BGP Role          |
| :-------| :-------------| :-------------| :------------------| :------------------|
| **R1** | Loopback0    | 1.1.1.1/32   | 2001:db8:1::1/128 | AS 65000 Border   |
| **R1** | eth1 (to R2) | 10.0.12.1/24 | 2001:db8:12::1/64 | -                 |
| **R1** | eth2 (to R3) | 10.0.13.1/24 | 2001:db8:13::1/64 | -                 |
| **R2** | Loopback0    | 2.2.2.2/32   | 2001:db8:2::2/128 | AS 65000 Internal |
| **R2** | eth1 (to R1) | 10.0.12.2/24 | 2001:db8:12::2/64 | -                 |
| **R3** | eth1 (to R1) | 10.0.13.3/24 | 2001:db8:13::3/64 | AS 65001 Provider |

## Task 0: Interface and Loopback Configuration
Before starting the BGP configuration, you must define the Loopbacks. In FRR, these are treated like any other interface.

### Configuration (R1)
```text
interface lo
 ip address 1.1.1.1/32
 ipv6 address 2001:db8:1::1/128
!
interface eth1
 ip address 10.0.12.1/24
 ipv6 address 2001:db8:12::1/64
```

### Configuration (R2)
```text
interface lo
 ip address 2.2.2.2/32
 ipv6 address 2001:db8:2::2/128
!
interface eth1
 ip address 10.0.12.2/24
 ipv6 address 2001:db8:12::2/64
```

---

## Task 1: The Internal Foundation (IGP)
Before BGP, our internal routers must know how to reach each other's Loopbacks. We will use static routes for simplicity in this lab.

### Configuration (R1)
```text
ip route 2.2.2.2/32 10.0.12.2
ipv6 route 2001:db8:2::2/128 2001:db8:12::2
```

### Verification
Ensure you can ping R2's loopback from R1:
```text
R1# ping 2.2.2.2
!!!!! (Success)
```

---

## Task 2: Establishing iBGP over Loopbacks
Now we establish the BGP session. In FRR, we must specify the `update-source` to ensure the TCP session initiates from the Loopback IP.

### Configuration (R1)
```text
router bgp 65000
 neighbor 2.2.2.2 remote-as 65000
 neighbor 2.2.2.2 update-source 1.1.1.1
 !
 address-family ipv4 unicast
  neighbor 2.2.2.2 activate
 exit-address-family
```

### Verification
Check the session state:
```text
R1# show ip bgp summary
Neighbor        V         AS   MsgRcvd MsgSent   TblVer  InQ OutQ  Up/Down     State/PfxRcd
2.2.2.2         4      65000        10      10        0    0    0 00:05:12            0
```
*Expected Result: State should be numerical (e.g., 0) or "Established", not "Active" or "Idle".*

---

## Task 3: Originating Prefixes (The Anchor)
We will announce `192.0.2.0/24` and `2001:db8:beef::/48`.

### Configuration (R1)
```text
ip route 192.0.2.0/24 blackhole
ipv6 route 2001:db8:beef::/48 blackhole
!
router bgp 65000
 address-family ipv4 unicast
  network 192.0.2.0/24
 exit-address-family
 !
 address-family ipv6 unicast
  network 2001:db8:beef::/48
 exit-address-family
```

### Verification
Check if R1 is actually announcing these:
```text
R1# show ip bgp self
Network          Next Hop            Metric LocPrf Weight Path
*> 192.0.2.0/24   0.0.0.0                  0         32768 i
```
*Expected Result: The `*>` symbols indicate the route is Valid and Best.*

---

## Task 4: Solving the Next-Hop Issue
R1 has an eBGP session with R3 (Provider). R3 is sending a route `100.64.0.0/10` to R1.

### Observation (on R2)
Check the route on the internal router:
```text
R2# show ip bgp
Network          Next Hop            Metric LocPrf Weight Path
* i 100.64.0.0/10   10.0.13.3                0    100      0 65001 i
```
*Expected Result: Notice the `i` (learned via iBGP) but the lack of a `>`. The Next-Hop `10.0.13.3` is inaccessible to R2!*

### The Fix (on R1)
```text
router bgp 65000
 address-family ipv4 unicast
  neighbor 2.2.2.2 next-hop-self
```

### Verification (on R2)
```text
R2# show ip bgp
Network          Next Hop            Metric LocPrf Weight Path
*>i 100.64.0.0/10   1.1.1.1                  0    100      0 65001 i
```
*Expected Result: The Next-Hop changed to `1.1.1.1` (R1's Loopback), which R2 knows how to reach. The route is now `*>` (Best).*

## Task 5: Controlled Redistribution
We want to redistribute R1's connected interfaces but ONLY the one used for the "Lab-Services" (`172.16.1.0/24`).

### Configuration (R1)
```text
ip prefix-list PL-SERVICES permit 172.16.1.0/24
!
route-map RM-SERVICES permit 10
 match ip address prefix-list PL-SERVICES
!
router bgp 65000
 address-family ipv4 unicast
  redistribute connected route-map RM-SERVICES
```

### Verification
Ensure other connected interfaces (like the one to R3) are NOT in the BGP table:
```text
R1# show ip bgp
...
*> 172.16.1.0/24   0.0.0.0                  0         32768 ?
```
*Expected Result: Only the permitted subnet appears. Other connected interfaces are filtered.*

---

## Task 6: Soft Resets
Modify the `RM-SERVICES` route-map to set a MED of 50, then apply the change without dropping the session.

### Configuration (R1)
```text
route-map RM-SERVICES permit 10
 set metric 50
!
! Apply change softly
clear ip bgp 2.2.2.2 soft out
```

### Verification (on R2)
```text
R2# show ip bgp 172.16.1.0
BGP routing table entry for 172.16.1.0/24, version 5
...
  Metric: 50, Localpref: 100, Weight: 0
```
*Expected Result: The Metric (MED) should now be 50.*

## Appendix: Containerlab Topology
You can use the following `lab2.clab.yml` file to instantiate the lab environment. This topology uses the official FRR image and sets up the links according to the addressing table.

```yaml
name: bgp-lab2

topology:
  nodes:
    r1:
      kind: linux
      image: frrouting/frr:latest
    r2:
      kind: linux
      image: frrouting/frr:latest
    r3:
      kind: linux
      image: frrouting/frr:latest

  links:
    - endpoints: ["r1:eth1", "r2:eth1"]
    - endpoints: ["r1:eth2", "r3:eth1"]
```

> **Note:** To run this lab, save the content above as `lab2.clab.yml` and run `sudo containerlab deploy -t lab2.clab.yml`. Once deployed, you can access the routers using `docker exec -it clab-bgp-lab2-r1 vtysh`.
